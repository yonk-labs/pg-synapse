This is the second scenario: the DBA that opens tickets. This one is about judgment. The agent has to decide what it can safely fix by itself, and what it must hand to a human.

The card explains the setup. A monitoring system has raised four health signals. One of them is safe to fix inside a transaction: a missing index. The other three are not: work mem, a concurrent reindex, and shared buffers.

Set up seeds the dba schema, the four signals, an audit log table, and registers the dba advisor agent. Like every scenario, it is reload safe, so you can reset it live.

Now the run. The suggested prompt is simply: review the pending health signals and act on each one. I click run.

The loop is running inside the Postgres backend. The agent's instructions give it one rule: only transaction safe changes may be applied directly. Anything that needs a concurrent build, a vacuum, or a server setting must become a ticket.

Each turn, the model reads a signal with a SQL query and decides. For the audit log, the right decision is a plain CREATE INDEX, which it is allowed to run itself.

For the other three, the right move is to write a row into dba dot recommendations, with a severity and a rationale, and mark the signal as handled. That is a ticket for a human.
