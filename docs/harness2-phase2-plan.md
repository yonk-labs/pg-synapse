# harness2 borrowings, phase 2: finish the turnover list

Started 2026-10-19 10:10 EST. Follows `harness2-borrowings-plan.md` (B1 to B12,
done) and `plexus/docs/TURNOVER.md` "Next steps".

## Goals

1. The tuner can climb on partial progress: a 4-of-5 rollout beats a 3-of-5
   one even when nothing passes the full assertion.
2. A run that hits the wall clock keeps its trajectory, so the tuner (and a
   human with `synapse.trajectory`) can see what the agent did before it ran
   out of time.
3. An existing v0.1.1 install can `ALTER EXTENSION pg_synapse_pgrx UPDATE` to
   the new objects.
4. `plexus/` is a git repo with sane ignores.

Out of scope here: pushing the branch / opening the PR (needs the owner's go),
stele as the lessons store (optional item 8), sidecar parity (tracked as a gap).

## Design

### Partial scoring (tune.py)

- New optional scenario file `conditions.sql`: one query returning rows of
  `(condition text, ok boolean)`. `assert.sql` stays the authority for
  "passed".
- `Roller.roll` runs it after the assertion and records `conditions`
  (name -> bool) and `score` (fraction true). Missing file -> `score` is 1.0
  or 0.0 from the assertion, so old scenarios behave as before.
- `select()`: full passes first (fewest tokens). Otherwise the best final by
  score, adopted only if its score beats the best base score; tie-break
  tokens. KEEP_BASE when no final beats the base.
- The score and condition names never reach the improver: `render_rollout`
  is unchanged and `conditions` stays out of the context tree. They appear in
  REPORT.md and summary.json only.
- `plexus/scenario/conditions.sql`: the five `bool_and` terms split out.

### Trajectory on timeout (pg-synapse-core)

- `ExecutionContext.progress: Option<ProgressSink>`; `ProgressSink` wraps
  `Arc<Mutex<ExecutorOutcome>>`.
- `LoopHarness` mirrors every appended message, issued tool call, usage
  update and trace event into the sink when present.
- `Runtime::execute_inner` creates a sink when a wall-clock budget is set; on
  `Elapsed` it returns the sink's snapshot with `status = TimedOut`, so the
  pgrx host's `log_execution` writes the execution row, messages and traces
  and returns an `execution_id`.

### Upgrade script

- `pg_synapse_pgrx--0.1.1--0.2.0.sql`: the DDL and function definitions the
  branch added (harness components, skills, tool hints, lessons, trajectory),
  generated by diffing the pgrx schema output of `main` against the branch.

## Implementation notes

### Partial scoring

- `Scenario.conditions_sql`, `parse_conditions()`, `tokens()` and the new
  branch in `select()` live in `bench/tune.py`. Scenarios without
  `conditions.sql` take the old path unchanged (full pass, then the
  "completed without error" provisional adoption).
- Choice: a final must beat the best base score, not the mean. With k=2 the
  mean rewards a base that got lucky once; the max is the honest bar for
  "better than what is live".
- Choice: `score` and `conditions` are stripped from `rollouts/<label>.json`.
  The Claude improver runs with Read/Glob/Grep and nothing stops it from
  reading outside its workdir, and condition names ("policy_version",
  "escalation") are the grader in words. They appear in `REPORT.md` and
  `summary.json`, which are written after the last improver call.
- Checked with synthetic rollouts: higher score wins, equal scores break on
  tokens, a final no better than the base is KEEP_BASE, a full pass still
  outranks any score.

### Trajectory on timeout

- `ProgressSink` (`types/outcome.rs`) is `Arc<Mutex<ExecutorOutcome>>` with
  `update` and `snapshot`; poisoning is recovered because every update is a
  push or an add.
- `LoopHarness::mirror` is called from `append` (every message),
  `record_event`, `record_usage` and the tool-call branch of
  `one_llm_turn_with`. Three executors share the harness, so all three get
  it.
- `Runtime::execute_inner` only creates a sink when the budget is non-zero.
  On `Elapsed` the snapshot's fields are kept and `status`/`duration_ms`
  overwritten.
- The pgrx host needed no change: `log_execution` already keys off
  `messages[0].execution_id`, and `should_persist_messages(false)` decides
  whether a non-completed run's messages are written (every level except
  `off`; `error` writes only failed runs, which now includes timeouts).
- Test: `runtime::tests::timed_out_run_keeps_its_partial_trajectory`
  (one tool call, then a 30 s hang against a 300 ms budget). Needed a
  `MockLlmProvider::set_delay_after(calls, delay)` helper.

### Upgrade script

- Generated by diffing `cargo pgrx schema` for `main` and the branch: seven
  new functions, none changed or removed. The script carries the agents
  columns, the three tables, the trajectory functions, the seven function
  definitions and the matching grants. `cargo pgrx package` installs it
  from `crates/pg-synapse-pgrx/sql/` with no extra config.
- Verified in a throwaway `plexus-db:dev` container: install 0.1.1 (from
  main's generated SQL), create an agent, `ALTER EXTENSION ... UPDATE TO
  '0.2.0'`, then compare functions with ACLs, columns, and relations with
  ACLs against a fresh 0.2.0 install: 165 objects, identical. The agent row
  survived and `skill_set` / `agent_harness` work on the upgraded database.
- Workspace version 0.1.1 to 0.2.0 across every `Cargo.toml`, path-dep
  versions included (per CLAUDE.md). Clients keep their own versions.

### Stronger model (TURNOVER step 5)

- Qwen3.6-35B-A3B NVFP4 (`qwen36-nvfp4`) on vLLM at 192.168.1.133:8000,
  thinking on. Tool calling works out of the box. Only the LLM profile
  changed; the tuned harness is the 4B one.
- First run wrote nothing: the model sends `http_post.body` as a
  JSON-encoded string, the Plexus API answered 422, 44 retries. Fixed in
  `plugins/pg-synapse-tools-http` (`decode_string_body`: a string that
  parses to an object or array is sent parsed). Unit test plus a wiremock
  test; gates 424 passed, 0 failed.
- Choice: fix the tool rather than add a tool hint. The 422 body does not
  match a useful hint pattern and every model that does this would need the
  same hint. The only request the decode changes is a string body that is
  itself JSON object or array text, which a caller rarely means to send
  double-encoded.
- Second run: 4 of 5 (refund decisions and policy_version pass for the
  first time). Audit failed on the 40-iteration cap after duplicate audit
  inserts and repeated lookups.
- `make tune K=2` on this model: all eight rollouts passed (base 2/2), so
  selection went by tokens: `agg1` adopted at 133k input tokens against
  195k to 227k for the base; lesson 2 written. `make run` on the adopted
  harness: 5/5, PASS, 24 iterations, 86 s, the first full pass.
- The running `plexus-db-1` got the new `.so` by `docker cp` plus restart
  (the compose service has no data volume, so a recreate wipes the tuned
  harness). The image itself was rebuilt from the same code.

## Next steps and gaps

- Partial scoring still has no live test: on Qwen3.6 every rollout passed.
  A `make tune K=2` on the 4B model (3 of 5) is the run that would use it.
- The `.so` in the running `plexus-db-1` was swapped in by hand; the image
  was rebuilt before a doc-comment-only move in `tools-http`, so rebuild it
  once more before the next `make up`.
- Sidecar parity: `sql/sidecar-install.sql` and the sidecar loader know the
  three agents columns but not skills, hints or lessons.
- `--exclude pg_synapse_pgrx` stays the local gate until pgrx gets a
  user-owned Postgres (`cargo pgrx init --pg17 download`).
- The tuner's evidence boundary relies on file placement, not a sandbox: the
  improver can still read `summary.json` from an earlier run if one exists
  under the same tree. Running each improver in a container or with
  `--add-dir` limits would close it.
- Push the branch and open the PR once the owner says go.
