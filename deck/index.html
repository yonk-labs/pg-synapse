A · What this is

An agent loop you call from SQL

pg_synapse is a Postgres extension, written in Rust, that runs the tool-calling loop where the data already is.

SELECT synapse.execute('triage_agent', 'Triage ticket 1'); -- the agent reads rows, calls the model, writes rows back, and returns an outcome envelope: -- status, tokens, cost, duration, tool calls, and the full message trace
Inside

The loop runs in the backend

Tools are SQL. Tool calls run over SPI, in the same database that holds the data.

Bring your own model

Any OpenAI-compatible endpoint

vLLM, llama.cpp, LM Studio, OpenAI. Anthropic and llama.cpp provider plugins too.

Open

Apache-2.0 / MIT

Built clean-room from public sources. Kernel has no I/O and no unsafe.

B · Why a loop in the database

Today the agent lives next to the database

An app-layer agent framework talks to Postgres like any other client, and that is where the trouble starts.

Credentials

A second set of keys

The agent service needs its own connection string, its own role, its own idea of what it may touch. Governance gets copied, then drifts.

Audit

The record lives elsewhere

What the agent did is in an app log or a vendor dashboard. What the database did is in Postgres. Joining them is a project.

Atomicity

The decision is outside the transaction

An agent that approves or rejects a write cannot roll that write back. It can only react afterwards.

Hops

A round trip per step

Every query the agent runs is a network hop, plus a service to deploy, scale and keep alive.

B · Why a loop in the database

Put the loop where the decisions are

1 · Governance

Inherits the database's

Tool SQL runs under Postgres privileges. GRANT, roles and ownership apply. “Permission denied” is the database doing its job.

2 · Decisions

Stay in the database

Inline mode runs the agent inside the writing transaction. Reject, and the INSERT rolls back with a reason.

3 · Hops

Fewer of them

Tool calls are in-process SPI, not client round trips. The model call is the one external hop.

4 · Evolution

Agents are rows

Prompt, tools and limits live in synapse.agents. Change them with SQL, version them in migrations, pg_dump takes them along.

5 · Audit

Just tables

Every run lands in synapse.executions, messages and traces. Query the agent's behaviour with the SQL you already know.

6 · Safety

Rails are settings

Max iterations, timeout and cost cap per agent. A savepoint per tool call. Cancel with pg_cancel_backend.

B · How it works

One loop, inside the transaction

Bounded by construction: every exit is a named status in the result envelope.

C · Architecture

Three tiers: SQL, host, kernel

C · Architecture

Can't load extensions? Run the kernel beside it

Managed Postgres (RDS, Cloud SQL, Neon, Supabase) will not load a custom .so. Same kernel, out of process.

  • Same agents, same synapse tables, seeded with plain DDL. No extension on the database.
  • The trade: tool calls cross the wire again, and the sidecar needs its own admin token and network path.
D · The thesis

What autonomous DB operations actually require

A model that can call tools is the easy part. These are the parts that make it safe to let it near production.

Bounded. Iteration, time and spend caps, enforced by the runtime, not the prompt.
Privilege-scoped. It can only do what its role can do. Same GRANTs as everyone else; queued runs use a dedicated role you grant.
Transactional. Writes roll back with a failing tool call. Inline agents can veto a commit.
Auditable. Every message, tool call and cost is a row you can query later.
Cancellable. An operator can stop a run mid-loop with a normal Postgres cancel.
Human-gated where it must be. What is not transaction-safe becomes a ticket, not an action.
Asynchronous when it should be. Queue mode commits instantly; a background worker runs the agent.
Testable. Each scenario ships a probe that goes FAIL then PASS. Behaviour you can assert.
D · Agents evolve like procedures

Agents are data, triggers are wiring

Define an agent with a function call. Attach it to a table. Change either with SQL.

-- an agent is a row: prompt, executor, model profile, tool allow-list, limits SELECT synapse.agent_create('policy_agent', 'Reject orders with a non-positive amount...', 'conversation', 'vllm-default', ARRAY['sql_query'], 15, 90000); -- inline mode: the agent runs inside the INSERT's transaction and can veto it SELECT synapse.attach_agent_trigger('demo.orders', 'policy_agent', 'inline', 'INSERT', NULL, 'NEW::text'); -- queue mode: the INSERT commits instantly, a background worker runs the agent SELECT synapse.attach_agent_trigger('demo.tickets', 'enrich_agent', 'queue', 'INSERT', NULL, 'NEW::text');

Stored in Postgres means it gets backups, replication, pg_dump, migrations and code review like everything else you ship.

D · Honest limits

What this does not do for you

  • It runs inside a transaction. So plain CREATE INDEX and DML are auto-appliable. CREATE INDEX CONCURRENTLY, VACUUM and ALTER SYSTEM are not, and become tickets for a human.
  • Models are the weak link. pg-one builds take 21 to 81 seconds on the reference stack, and not every build finishes: 4 of 6 observed builds completed. Small local models stumble on long tool calls.
  • An inline agent holds a backend. Inline mode is bounded by a timeout setting, and a slow model needs a bigger budget than the 2 second default.
  • The demo is single-user. No auth and no TLS on the demo UI. Do not expose it to a network you do not trust.
  • Out of scope on purpose: RAG and chunking, vector storage, multi-agent crews, NL2SQL, streaming over SQL. Those are plugins or later.
